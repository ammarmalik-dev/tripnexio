# TripNexio - Project Context

## What this is
TripNexio is a travel and visa services platform. Customers request visa and flight services online. Requests become LEADS in a CRM. Staff process them MANUALLY with vendors/airlines. This is NOT a self-service live-booking engine. There is NO live flight/visa booking API. Do not add one.

## Scope (locked)
Market: India to UAE/GCC only (UAE, Saudi Arabia, Bahrain, Kuwait, Oman, Qatar). NOT worldwide.
Modules: New Visa, Visa Extension, Visa Change (Airport-to-Airport + Border Exit), Flight Special Fare, Return Verified Ticket, OTB, Track Status, Ask TripNexio AI, CRM, Admin.

## Stack
Next.js (App Router) + TypeScript (strict), Tailwind CSS, framer-motion for animation, lucide-react for icons, Prisma ORM + PostgreSQL, Auth.js (NextAuth), zod + react-hook-form for validation, Node. Deployment later on Hostinger VPS (Coolify/Nixpacks).

## Auth
Email/Password + Google OAuth + Guest checkout. NO WhatsApp/SMS OTP. Guests can browse and start requests but must log in to view history/tracking. **This describes customer-facing auth (not yet built — the M1 `/login`/`/register` pages are still UI mockups with no real backend).** Staff/CRM auth is a separate, already-implemented system — see "Progress so far — CRM workspace" below; it does not use Auth.js and is not what this section describes.

## Milestones
M1: Frontend/UI (glassy, animated, responsive). M2: DB + APIs + Auth + CRM core. M3: Admin + RBAC + integrations + deployment.

## Design direction
Premium travel look at or above the quality of Atlys.com and Visa2fly.com. **Light-first base** — warm-white/white content surfaces with dark-navy text, confirmed against both `docs/brand/Brand_Foundation.md` §13 (Glass 01/02/03 are explicitly white-based, `rgba(255,255,255,.86/.92/.96)`; dark glass is called out as needing "its own validated treatment," i.e. the exception, not the default) and the client-approved reference (`BRAND ASSEST/refrence-desgin-home.webp`, verified by pixel-sampling, not just eyeballing). Glassmorphism (backdrop blur, soft 1px navy-tinted borders, layered translucent white surfaces), a refined electric-blue accent gradient for primary CTAs/highlights, and a small number of deliberately dark-navy blocks (footer, bottom CTA banner, "Track Your Journey"-style status cards) for contrast and emphasis — not a sitewide dark theme. Subtle gradient-mesh backgrounds where used, smooth scroll-reveal and hover micro-interactions, clean cards, generous spacing, confident modern typography. Motion should feel alive but tasteful, never gaudy. Mobile and desktop both first-class.

## QUALITY STANDARDS (apply to everything)
- TypeScript strict, no `any`. Share zod schemas between client, server, and API. Use react-hook-form on all forms with inline validation.
- Every data view has three states: loading skeleton, empty state, and error state. Never a blank screen.
- Use toast notifications for success/error feedback on all user actions.
- Accessibility: semantic HTML, keyboard navigation, visible focus states, aria labels, sufficient contrast, and respect prefers-reduced-motion (reduce/disable animations when set).
- SEO: per-page metadata and Open Graph tags using the TripNexio socials below. Add sitemap and robots.
- Performance: next/image for images, lazy-load below the fold, optimize fonts, prefer Server Components, use Client Components only where interactivity is needed.
- Security: validate every mutation server-side, enforce RBAC server-side (never rely on hidden UI), rate-limit auth endpoints, sanitize inputs, set secure headers, keep all secrets in env only.
- Error handling: try/catch on all API routes, a consistent error response shape, never leak internals to the client.
- Write every state change to the AuditTrail.
- No hard-coded brand colors anywhere; use design tokens so branding swaps in minutes.
- Reusable components, no duplication.

## Progress so far — Service request flows (M1 frontend, mock data)
Beyond the homepage, two service modules now have real routes: **OTB** (`/services/otb`, `/services/otb/request`) and **New Visa** (`/services/new-visa`, `/services/new-visa/request`). Both are frontend-only against mock APIs — no backend exists yet. This is the pattern the remaining modules (Visa Extension, Visa Change, Flight Special Fare, Return Verified Ticket) should follow:

- **Generic multi-step orchestrator**: `src/components/forms/MultiStepRequestFlow.tsx` is a generic `<T extends FieldValues>` component that owns the stepper, per-step zod validation (`methods.trigger(stepFields[currentIndex])`), loading/error/success state, and the animated step transitions. Each service only supplies: a zod schema (with a `stepFields: Record<number, (keyof T)[]>` map and `stepLabels: string[]`), an array of step components, a mock submit function returning `{ referenceId }`, and success copy. See `OtbRequestFlow.tsx` / `NewVisaRequestFlow.tsx` for the ~20-line composition pattern — copy one of these first when starting a new flow, don't rebuild the stepper.
- **Shared success state**: `src/components/forms/RequestSuccessPanel.tsx` renders the post-submit reference-ID screen for any flow — do not create a per-service success panel.
- **Shared field primitives**: `src/components/forms/{FormField,TextField,SelectField,DateField,RadioCardGroup,Stepper,useMultiStepForm}.tsx` — reuse these for any new field, don't hand-roll inputs.
- **Critical gotcha already fixed once** (see `feedback_button_type_toggle_race` in memory): every nav button in a step flow must stay `type="button"`, including the final submit button, which calls `methods.handleSubmit(onSubmit)` directly from `onClick`. Never let a button's `type` flip to `"submit"` based on step state — `MultiStepRequestFlow` already does this correctly, so as long as new flows go through it, this class of bug can't reappear.
- **Schema pattern**: per-step zod object schemas merged via `.extend()` into one request schema (see `otb-schema.ts` / `new-visa-schema.ts`). Prefer keeping a field's schema type as a plain `string` when the input is a native `<input>`/`<select>` (not `z.coerce.number()`) — react-hook-form's uncontrolled `register()` reads/writes the DOM as a string, and `MultiStepRequestFlow`'s generic typing assumes the schema's Input type equals its Output type (`ZodType<T, T>`); a coercing schema (Input ≠ Output) breaks that generic and won't type-check.
- **Sample vs. real data**: `src/lib/sample-data.ts` holds all cross-flow illustrative options (airlines, visa types) with a `*_CAPTION` string to render next to the field per hard rule #1. Destination countries (`DESTINATION_COUNTRY_OPTIONS`) are NOT sample data — they're the actual locked market scope from this file's "Scope" section above, so they render without a sample caption.
- **Verified pattern for testing a stepper in Chrome**: native `<select>` dropdowns render as an OS-level popup that `computer` click coordinates can miss unreliably (clicking a visible option in a screenshot can silently no-op). Focus the select and use `key: "Down"` + `key: "Return"` instead — reliable every time. Also watch for pre-filled defaultValues (e.g. a "Number of Travelers" field defaulting to `"1"`) before typing into a field — a plain click+type appends to existing text instead of replacing it; use `triple_click` first to select-all.

## Progress so far — Database (M2 start)
The Prisma schema now exists (`prisma/schema.prisma`) with an initial migration applied to a local dev database. As of the lead-creation API below, the OTB and New Visa frontend flows are wired to it for real — see the next section.

- **Schema**: Customer 360 (Customer → Passengers/Leads/Bookings) → Lead → Quotation → Booking → Payment → Refund, plus Document (polymorphic to Passenger/Booking), AuditTrail (polymorphic entityType+entityId), Vendor, admin-managed masters (Airport, Airline, Border, DocumentRequirement, Faq), and RBAC (User/Role/Permission, many-to-many). Every status field is an enum; every FK and status/boolean-flag field used for filtering has an explicit `@@index`. **`LeadStatus`, `BookingStatus`, and `RefundStatus`'s exact enum *values* were my proposed default lifecycle** (not specified when the schema was requested) — review these before relying on them; `ServiceType`, `PaymentStatus`, and `DocumentStatus` values came directly from the request. `Quotation.margin` and `Refund.refundAmount` are plain stored columns the API layer must compute and write (sellingPrice − vendorCost, paidAmount − cancellationCharge − gatewayCharge) — not DB-generated columns.
- **Prisma major-version gotcha**: this project pins `prisma`/`@prisma/client` to `7.10.0` explicitly in package.json — the unqualified `latest` dist-tag currently resolves to an `8.0.0-rc.13` release candidate (also reproducibly crashed npm's own dependency resolver with `Cannot read properties of null (reading 'edgesOut')` on this machine — an unrelated npm/arborist bug, but pinning avoided it anyway). **Never bump prisma/@prisma/client with a bare `npm install prisma@latest`** — check `npm view prisma dist-tags` first and pick an actual stable version.
- **Prisma 7 architecture change**: `schema.prisma`'s `datasource` block no longer takes a `url` — the connection string lives in `prisma7.config.ts` at the project root (CLI-only: `migrate`/`db seed`/`studio` read it), and the generator is `provider = "prisma-client"` (not the old `prisma-client-js`) outputting real `.ts` source to `src/generated/prisma` (gitignored, regenerate with `npm run db:generate`; also excluded from ESLint in `eslint.config.mjs`). The **runtime** `PrismaClient` is separate from the CLI config and now requires an explicit driver adapter — see `src/lib/db.ts`, which builds one from `@prisma/adapter-pg` + `pg` and memoizes the client on `globalThis` (so Next.js dev hot-reload doesn't spin up a new connection pool on every edit). Import the generated client via a relative path (`../generated/prisma/client`), not the `@/` alias — `tsx` (used to run `prisma/seed.ts` and any future standalone scripts) doesn't resolve tsconfig path aliases the way Next.js does.
- **Local dev database**: this machine already had an unrelated Postgres server on port 5432 (bundled with a separate Odoo installation) whose credentials nobody had — rather than touch that install's config to recover/reset them, M2 runs its own fully separate instance via `npx prisma dev --name tripnexio --detach` (a Prisma-managed local Postgres, own port, own `.env`, zero shared state with the Odoo one). `npx prisma dev ls/start/stop/rm` manages its lifecycle; if `npx prisma migrate dev`/`db:seed` ever fail with a connection error, this dev server has likely stopped (e.g. after a reboot) — restart it and update `.env`'s port if it changed.
- **Seed data**: `prisma/seed.ts` only inserts the RBAC bootstrap rows genuinely needed to run the app (Admin/Staff roles + a small permission set) plus a handful of masters rows explicitly named "Sample ..." (e.g. "Sample Airport 1", code `SA1`) so they can never be mistaken for real airports/airlines/borders — per hard rule #1. Run it with `npm run db:seed`.
- **npm scripts added**: `db:generate`, `db:migrate` (→ `prisma migrate dev`), `db:seed`, `db:studio`.

## Progress so far — Lead-creation API (M2)
Every service now has a real, working lead-intake API route, and OTB + New Visa's frontends call it for real (no more mock submit).

- **Shared pipeline**: `src/lib/leads/create-lead.ts`'s `createLeadFromSubmission()` is the one function every service route calls. It runs one `db.$transaction`: match-or-create a `Customer` by mobile (falls back to email), match-or-create a `Passenger` by name under that customer (case-insensitive — this is how "returning customers reuse existing passengers" is satisfied without a schema change), create the `Lead` (`details` JSON gets a `passengerIds` array folded in — the schema has no Lead↔Passenger join table, so this is how a lead's passengers are tracked today; a real join table is the fix once multi-named-passenger UI exists), and write an `AuditTrail` row. Reuse this for any new service — don't hand-roll Customer/Passenger matching again.
- **Lead references**: `src/lib/leads/reference.ts`'s `formatLeadReference(serviceType, leadId)` derives the customer-facing reference (e.g. `OTB-JYOQHX`) from the real Lead id's last 6 characters — replaces the M1 mock's `Date.now()`-based ids. This is a *lead* reference, distinct from `Booking.bookingId` (`TNX-XX-XXXXXX`) — see the CRM API section below for exactly when that gets assigned.
- **One route per service** under `src/app/api/leads/{otb,new-visa,visa-extension,visa-change,flight-special-fare,return-ticket}/route.ts`. Each validates the request body against that service's own zod schema (the exact same schema object the frontend's `zodResolver` uses, where a frontend exists — `otb-schema.ts`/`new-visa-schema.ts`), then calls `createLeadFromSubmission`. **Visa Extension and Visa Change have schemas and routes but no frontend yet** (only OTB and New Visa do) — they were built to spec anyway per the explicit business rules below, and are only reachable/tested via direct API calls today.
- **Consistent response shape**: `src/lib/api/respond.ts` (`jsonSuccess`/`jsonError` → `{ data }` / `{ error: { message, fieldErrors? } }`) and `src/lib/api/client.ts` (`postJson`, throws `ApiError` with the parsed message/fieldErrors) — every route and every frontend caller goes through these, don't invent a one-off shape.
- **Spec rules enforced server-side, not just by frontend field omission** (per CLAUDE.md's own "validate every mutation server-side"): OTB's schema has no nationality field at all, and `createLeadFromSubmission` strips one defensively if it ever shows up anyway. Visa Extension's `entryDate` has no `.optional()`. Visa Change's schema (`visa-change-schema.ts`, a `z.discriminatedUnion` on `changeType`) only accepts `departureAirportId`/`arrivalAirportId`/`borderId` — master-record ids from a future `<select>`, never free-text names — and the route additionally does a live DB lookup confirming the id is a real, active `Airport`/`Border` row before creating the lead.
- **Frontend wiring**: `src/lib/api/{otb,new-visa}.ts` replaced the old `src/lib/mock-api/{otb,new-visa}.ts` (deleted) — same function signature, now calls the real endpoint via `postJson`. `MultiStepRequestFlow.tsx` gained `toast.success`/`toast.error` calls (sonner) alongside its existing inline success/error states.
- **Verification note**: end-to-end browser testing hit repeated Chrome-tool renderer freezes/screenshot timeouts in this session (`CDP sendCommand "Page.captureScreenshot" timed out`) unrelated to the app itself — when that happens more than once or twice in a row, it's faster and just as rigorous to verify a route directly with `fetch`/`node` against `localhost:3000` and check the resulting rows in Postgres, rather than keep fighting the browser tool. That's how Visa Extension/Visa Change/Flight Special Fare/Return Ticket were verified this round (they have no frontend to click through anyway).

## Progress so far — Quotation/Booking/Payment/Document API (M2, CRM backend)
This is the API layer the CRM/staff UI (and eventually a customer payment page) calls. All of it is `getStaffSession()`-gated now (Quotation routes were retrofitted when the CRM quote builder went live; Booking/Payment/Document routes were retrofitted when their CRM screens went live — see "Progress so far — CRM operational screens") — don't expose any of it to unauthenticated customers as-is when a real customer-facing flow eventually needs a payment/tracking page; that will need its own, differently-scoped auth check, not staff session reuse.

- **Quotation** (`src/app/api/quotations`): `POST` (`leadId` + vendor/flight fields — `margin` is always `sellingPrice - vendorCost` computed server-side, never accepted from the client), `GET ?leadId=` (list), `PATCH /[id]` (update, recomputes margin from whichever of vendorCost/sellingPrice changed). `PATCH /[id]/select` is the one-active-quotation rule: it sets the target `isSelected=true` and, for every *other* quotation on the same lead, `isSelected=false` **and** `isExpired=true` — selecting one always expires its siblings, not just deselects them. Also moves the Lead to `QUOTED` (only if it isn't already `QUOTED`/`CONVERTED`).
- **Expiry**: `src/lib/quotations/sync-expiry.ts`'s `isExpiredNow()` checks `isExpired || validityExpiresAt < now`; `syncExpiredQuotations()` lazily flips `isExpired` (and writes an AuditTrail `EXPIRE` row) for any quotation whose `validityExpiresAt` has passed, since there's no cron/background job in M2 — it runs on every quotation list and select. A quotation that's `isExpiredNow()` can't be selected (409) or booked (409).
- **Booking** (`src/app/api/bookings`): `POST` (`quotationId` — the quotation must be selected and not expired; rejects with 409 if the lead already has a non-cancelled booking) creates the `Booking` row immediately (`Booking.bookingId` is a required unique column with no DB default) but only with a **placeholder** id from `src/lib/bookings/reference.ts`'s `placeholderBookingId()` (`PENDING-<random>`, unrelated to the row's own id — there's no way to know the row's id before it's created). The **real** `TNX-XX-XXXXXX` id (`formatBookingId`, 2-letter codes matching the schema's own doc comment: NV/VE/VC/FF/RT/**OT**) is only assigned at payment success. `PATCH /[id]/status` transitions go through `src/lib/bookings/transitions.ts`'s explicit allowed-transitions map (proposed default lifecycle, same caveat as the enum values themselves) — an invalid jump (e.g. `CONFIRMED` → `PENDING`) is a 409, not silently accepted.
- **Payment** (`src/app/api/bookings/[id]/payments`, `/api/payments/[id]/mark-success`): no gateway is integrated (that's Phase 5A) — `amount`/`gstAmount`/`gatewayFee` are computed from the booking's selected quotation using **clearly-labeled SAMPLE rates** (5% GST, 2% gateway fee, both named `SAMPLE_*_RATE` in code) standing in for real admin-configured tax/fee settings (Phase 4D). `mark-success` is the manual stand-in for a real gateway webhook — in one transaction it flips the Payment to `SUCCESS`, assigns the Booking's real id and moves it to `CONFIRMED`, and moves the Lead to `CONVERTED`. Only one `PENDING` payment is allowed per booking at a time.
- **Document** (`src/app/api/documents`): `POST` creates a requirement against a `passengerId` and/or `bookingId` (at least one required); `PATCH /[id]/status` sets any `DocumentStatus`; `PATCH /[id]/upload` accepts an already-hosted `fileUrl` (no storage integration here — that's a future concern) and auto-advances `REQUIRED`/`MISSING` to `RECEIVED`.
- **Shared audit helper**: `src/lib/audit/log.ts`'s `writeAudit(tx, {...})` — every route above (and the lead-creation pipeline, refactored to use it too) writes through this instead of calling `tx.auditTrail.create` inline. Use it for any new mutation.
- Verified end-to-end via a script hitting these routes directly (lead → 2 quotations → select expires the other → booking → payment → mark-success → status transition → document create/status/upload), including the negative cases (book-before-select, book-an-expired-quotation, duplicate-active-booking, duplicate-pending-payment, invalid-status-transition, select-an-expired-quotation) and a full AuditTrail read-back confirming every step was recorded in order.

## Progress so far — CRM workspace (Phase 3A)
The staff CRM now exists at `/crm/**`, with real (non-Auth.js) staff authentication and one fully-built section (Leads); every other sidebar item is a placeholder page.

- **Staff auth is intentionally separate from the customer Auth.js plan** in the Auth section above (which is still unbuilt). It's a small, self-contained JWT-cookie system scoped to staff only: `src/lib/auth/staff.ts` (`authenticateStaff` — bcrypt against `User.passwordHash`), `src/lib/auth/session.ts` (`jose`-signed JWT, `SESSION_COOKIE_NAME`/`SESSION_TTL_SECONDS`, 8h expiry), `src/lib/auth/staff-session.ts` (`getStaffSession()` — the *authoritative* check: re-verifies the User is still `active` in the DB, not just that the JWT is validly signed). `POST /api/crm/auth/login` (rate-limited via `src/lib/auth/rate-limit.ts`, generic "Invalid email or password" that never reveals which part was wrong) and `POST /api/crm/auth/logout` issue/clear the cookie.
- **Two-layer enforcement**: `src/proxy.ts` (Next.js 16 renamed `middleware.ts` → `proxy.ts`; the exported function must be named `proxy`, not `middleware` — the old name now just prints a deprecation warning at build) does a fast, Edge-compatible JWT-signature-only check on every `/crm/**` request except `/crm/login`, redirecting signed-out visitors to `/crm/login?from=<path>` before the page even renders. It **cannot** query the database (Prisma's `@prisma/adapter-pg` needs Node's `pg`, not available in the Edge runtime) — the authoritative, DB-backed check is `getStaffSession()`, called again in `src/app/crm/(authenticated)/layout.tsx` (redirects) and in every CRM API route that needs it (401s). Every CRM API route now has this check — `GET /api/leads`, `/api/leads/[id]/**`, `/api/staff`, `/api/vendors`, `/api/quotations/**`, `/api/bookings/**`, `/api/payments/**`, `/api/refunds/**`, and `/api/documents/**`.
- **Hiding the marketing chrome on `/crm/**`**: rather than restructuring the whole app into route groups with separate root layouts (the "textbook" Next.js fix), `src/components/layout/HideOnCrm.tsx` wraps `<Navbar />`/`<Footer />` in the single root layout and renders `null` when `usePathname()` starts with `/crm` — a Client Component making a pathname-based decision about Server Component children passed into it. ## Progress so far — CRM lead detail page (Phase 3B)

## Progress so far — CRM quote builder (Phase 3C)
Staff can now build and select quotes directly from the lead detail page (`QuoteBuilder.tsx`, in the main column). No live pricing search anywhere — every number is staff-entered.

- **One `Quotation` model, two quote shapes**: rather than a separate model per service type, `Quotation` gained nullable columns for both shapes and a shared helper (`src/lib/quotations/pricing.ts`) decides which applies from the **lead's own `serviceType`, fetched server-side** — never trusted from the client. `isFlightQuote(serviceType)` is true only for `FLIGHT_SPECIAL_FARE`; every other service type (visa services, Return Ticket, OTB) gets the simple shape. This was a judgment call — the task explicitly named "Visa services and OTB", and Return Ticket wasn't specified either way, but it isn't Flight Special Fare's structured fare/route form either, so it defaults to the simple fee-based shape too; revisit if Return Ticket turns out to need its own fare fields.
  - **Flight Special Fare fields**: `airline`, `flightNumber`, `route`, `flightDateTime` (departure), `arrivalDateTime`, `baggageAllowance`, `fareType`, `adultFare`/`childFare`/`infantFare`. `sellingPrice` is staff-entered directly (not derived from the fares — there's no passenger-count field on a quotation to multiply by).
  - **Visa/OTB fields**: `feeAmount`, `fineOrCharges`. `sellingPrice` (shown to staff as "Total") is computed server-side as `feeAmount + fineOrCharges` — the same never-trust-the-client pattern as `margin`.
  - `vendorCost` and `margin` (`sellingPrice - vendorCost`) are universal across both shapes and are the two fields **never sent to a customer-facing view** — there's no live customer portal yet, but `QuoteCard.tsx` visually marks them "(internal)" and any future customer-facing quotation serializer should omit them, not just hide them client-side.
- **Alternative routes**: reuses the schema's existing `alternativeOfId` self-relation (a quotation can point at the sibling quotation on the same lead it stands in for) rather than adding a new boolean — `QuoteBuilderForm.tsx` offers an "Alternative Route" select only for flight quotes, and `QuoteCard.tsx` renders an "Alternative Route" badge. Critically, the UI always renders that quotation's *own* `route` field — nothing in the alternative-quote render path ever reads the lead's originally-requested route, so it can't accidentally display as the requested one.
- **Validity cap**: `assertValidityWithinCap()` in `pricing.ts` rejects (400) a flight quote's `validityExpiresAt` more than `FLIGHT_QUOTE_MAX_VALIDITY_MINUTES` (30) minutes out — enforced only for flight quotes, no cap for the simple shape (not specified). `QuoteCountdown.tsx` ticks a live "Expires in mm:ss" (shared `now` state in `QuoteBuilder.tsx`, one `setInterval` for the whole card list) and a card's Select button disables itself the instant the client-side countdown hits zero, ahead of the next server-side lazy-expiry sync.
- **Selecting one still expires the others**: reused `PATCH /api/quotations/[id]/select` and `syncExpiredQuotations()` as-is from the earlier Quotation API work — no changes needed there beyond adding `getStaffSession()` gating and `byUserId` attribution on the audit rows.
- **New route**: `GET /api/vendors?service=<ServiceType>` (staff-gated, active vendors only) feeds the vendor `<select>`. Seed gained a second sample vendor, `Sample Flight Consolidator` (`FLIGHT_SPECIAL_FARE`), alongside the existing `Sample Vendor A` (`NEW_VISA`) — there's no seeded OTB vendor yet, so an OTB/visa quote in a fresh dev DB must currently pick a vendor tagged for a different service (the API doesn't enforce vendor-service matching); add an OTB sample vendor before relying on that filter for real.
- **Migration note**: adding the new `Quotation` columns hit a stuck shadow-database on this machine's local `prisma dev` instance (`type "ServiceType" already exists` on every `migrate dev` attempt, even after a full `migrate reset` and recreating the `tripnexio` instance from scratch) — worked around by diffing the live schema directly (`prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`, since Prisma 7 removed `--from-url`), applying that SQL by hand, and recording it with `prisma migrate resolve --applied` so it's still a normal tracked migration file in `prisma/migrations/`. If `migrate dev` starts throwing this same P3006 error again, this is the recovery path — no need to repeat the full reset dance.

Every mutation's `AuditTrail` row was confirmed to carry the correct `byUserId`. **Not yet visually verified in a browser** — the Chrome automation extension wasn't connected this session; do a real click-through of `QuoteBuilderForm`/`QuoteCard` before treating the UI itself (as opposed to the API) as fully confirmed.
