# TripNexio - Project Context

## What this is
TripNexio is a travel and visa services platform. Customers request visa and flight services online. Requests become LEADS in a CRM. Staff process them MANUALLY with vendors/airlines. This is NOT a self-service live-booking engine. There is NO live flight/visa booking API. Do not add one.

## Scope (locked — updated 2026-09-28, supersedes the original UAE/GCC-only scope)
Market: **worldwide**. This was a client-directed pivot: `TripNexio_Homepage_FINAL_Locked_Developer_Handover_1of1.docx` §1 says "TripNexio is positioned for worldwide visa and travel services; do not use UAE/GCC-only messaging", and `TripNexio_Developer_Business_Rules_All_Questions_Locked_v2.0.md` §6 says "India + GCC is Phase 1... Admin must be able to add future countries/markets without core redesign". Phase 1 connectivity (airports/airlines/services) covers India, UAE, Saudi Arabia, Bahrain, Kuwait, Oman, Qatar and Thailand. The *positioning*, homepage copy and imagery must never read as UAE/GCC-exclusive, and Admin must support adding further countries/markets without a redesign. Do not reintroduce UAE/GCC-only headings, destination labels or footer claims anywhere customer-facing.
Modules: New Visa, Visa Extension, Visa Change (Airport-to-Airport + Border Exit), Flight Special Fare, Return Verified Ticket, OTB, Track Status, Ask TripNexio AI, CRM, Admin.
The client's locked spec lives in `client-message/` (`CRM.md`, `ADMIN.md`, per-service `.md` files, audits) and `docs/*.docx` (final handovers). `docs/last_prompt.md` holds the P01–P27 task list with a `STATUS: DONE` line per finished task. Check these before proposing new work.

## Stack
Next.js 16 (App Router) + TypeScript (strict), Tailwind CSS 4, framer-motion, lucide-react, Prisma 7 ORM + PostgreSQL, hand-rolled JWT-cookie auth (`jose` + `bcryptjs`; **not** Auth.js/NextAuth), zod + react-hook-form, sonner toasts, vitest. Integrations: Razorpay, Resend, WhatsApp Cloud API, Anthropic SDK. Exact versions are in `package.json`/`package-lock.json` (see README). Production: **tripnexio.com on a Hostinger VPS via Coolify** (Dockerfile build, Postgres container); the old Vercel + Neon demo is stale. See `docs/deployment/DEPLOYMENT_RUNBOOK.md`.

## Auth
Email/Password + Google Sign-In + Guest checkout. NO WhatsApp/SMS OTP (the only OTP is an **email** code, `CustomerOtp`, used to prove ownership before claiming a password-less guest Customer at registration). Guests can browse and start requests but must log in to view history/tracking.
- **Customer sessions**: `src/lib/auth/customer.ts`, `customer-session.ts`, `get-customer-session.ts` (signed with `CUSTOMER_SESSION_SECRET`). Routes: `/api/auth/{login,register,logout,me,forgot-password,reset-password}`. `/login`, `/register`, `/forgot-password`, `/reset-password` and `/account` (the signed-in customer's leads, bookings, documents and deliveries) are real. Registration attaches prior guest history by mobile/email after email-OTP verification.
- **Google Sign-In (P09)**: `/api/auth/google/start` + `/callback`, `src/lib/auth/google.ts`. Works for customers and staff; staff Google login only matches an existing active `User` and never creates staff. When `GOOGLE_CLIENT_ID`/`SECRET` are placeholders, the buttons are hidden and the routes return 404. It has only been tested in the not-configured state.
- **Staff auth** is a separate system: see "CRM & Admin core" below. Staff password reset (`/api/crm/auth/{forgot-password,reset-password}`) bumps `User.sessionVersion`, which revokes existing sessions.

## Design direction
Premium travel look at or above the quality of Atlys.com and Visa2fly.com. **Light-first base**: warm-white/white content surfaces with dark-navy text. This was confirmed against both `docs/brand/Brand_Foundation.md` §13 (Glass 01/02/03 are white-based, `rgba(255,255,255,.86/.92/.96)`, and dark glass is the exception) and the client-approved reference `BRAND ASSEST/refrence-desgin-home.webp`, verified by pixel-sampling rather than by eye. Use glassmorphism (backdrop blur, soft 1px navy-tinted borders, layered translucent white surfaces), a refined electric-blue accent gradient for primary CTAs and highlights, and only a few deliberately dark-navy blocks for contrast: the footer, the bottom CTA banner and "Track Your Journey"-style status cards. It is not a sitewide dark theme. Keep gradient-mesh backgrounds subtle, and use smooth scroll-reveal and hover micro-interactions, clean cards, generous spacing and confident modern typography. Motion should feel alive but tasteful. Mobile and desktop are both first-class.

## QUALITY STANDARDS (apply to everything)
- TypeScript strict, no `any`. Share zod schemas between client, server, and API. Use react-hook-form on all forms with inline validation.
- Every data view has three states: loading skeleton, empty state, and error state. Never a blank screen.
- Use toast notifications for success/error feedback on all user actions.
- Accessibility: semantic HTML, keyboard navigation, visible focus states, aria labels, sufficient contrast, and respect prefers-reduced-motion (reduce/disable animations when set).
- SEO: per-page metadata and Open Graph tags using the TripNexio socials below. Sitemap and robots exist (`src/app/sitemap.ts`, `robots.ts`).
- Performance: next/image for images, lazy-load below the fold, optimize fonts, prefer Server Components, use Client Components only where interactivity is needed.
- Security: validate every mutation server-side, enforce RBAC server-side (never rely on hidden UI), rate-limit auth and public endpoints, sanitize inputs, set secure headers, keep all secrets in env only.
- Error handling: try/catch on all API routes, a consistent error response shape, never leak internals to the client.
- Write every state change to the AuditTrail.
- No hard-coded brand colors anywhere; use design tokens so branding swaps in minutes.
- Reusable components, no duplication.
- Vendor cost and margin are internal: never serialize them to a customer-facing response (omit them, don't just hide them). Staff views need `vendors.viewCost` or `finance.manage`.

## Verification & environment gotchas (read before running anything)
- After each unit run `npx tsc --noEmit`, `npm run lint`, `npm test` and `npm run build`. Trust these over IDE inline diagnostics, which have been stale here. Also do a visual check in Chrome when UI changed. To judge fidelity against a reference image, pixel-sample it (Python/Pillow) instead of eyeballing.
- **Local build single-worker workaround** (environmental, never commit it): a local `npm run build` against the `prisma dev` DB can fail prerendering `/` with `P1017 ConnectionClosed`, because parallel static-generation workers overwhelm it. Temporarily add `experimental: { cpus: 1 }` to `next.config.ts`, restart the DB, build, then restore the file and confirm `git diff next.config.ts` is empty. The same pages build fine on Vercel against Neon.
- **`prisma dev` ConnectionClosed / P1017** after heavy traffic: run `npx prisma dev stop tripnexio && npx prisma dev start tripnexio` (data is untouched), restart the Next dev server, and update `.env`'s port if it changed. Multi-query read screens use `runSequentially()` (see P24) partly for this reason.
- **Next dev stale cache**: if a long-running dev server starts 404-ing real routes or compiling very slowly, `rm -rf .next` and restart before assuming the code broke.
- **Chrome tool flakiness**: after 2+ CDP screenshot timeouts or a frozen renderer, verify via direct `fetch` against `localhost:3000` plus a Postgres read instead of retrying. For native `<select>`s, focus the element and use `Down` + `Return` keys (clicking an option by coordinates can silently no-op). Before typing into a pre-filled field, `triple_click` it first. Mobile-viewport resizing via the Chrome tool has been unreliable.
- **Test scripts**: the shared dev DB accumulates data, so query for the exact state a test needs instead of grabbing the newest row. The AuditTrail/DB is the authoritative check, not tailed log output. Raw `pg` client reads *and* writes of `timestamp without time zone` columns are parsed as local time: use Prisma's read path, `to_char()`, or naive-ISO `::timestamp` casts.
- **Rules from the task list** (apply to every P-task): never run `prisma migrate reset` or `db push`, never drop/truncate tables or delete existing data, never connect to or modify the production DB. Make schema changes only via `prisma migrate dev --create-only`, review the SQL, then apply locally. No unrelated refactors. Commit each task as one unit.

## Architecture notes & gotchas (still true)
- **Prisma 7**: `prisma`/`@prisma/client` are on 7.10.0. **Never** `npm install prisma@latest`: the `latest` tag resolved to an `8.0.0-rc` release, and a bare install also crashed npm's resolver (`edgesOut`). Check `npm view prisma dist-tags` first. The datasource URL lives in `prisma7.config.ts` (CLI only: migrate/seed/studio). The generator is `prisma-client`, which outputs to `src/generated/prisma` (gitignored, excluded from ESLint). The runtime client in `src/lib/db.ts` needs the `@prisma/adapter-pg` driver adapter and is memoized on `globalThis`. Standalone scripts run with `tsx` and must import the client by relative path (`../generated/prisma/client`), not `@/`.
- **Shadow DB drift (P3006 "type already exists")**: if `migrate dev` gets stuck, generate SQL with `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`, apply it by hand, and record it with `prisma migrate resolve --applied`. It stays a normal tracked migration file.
- **Migration backfills**: to add a `NOT NULL` column to a populated table, add it nullable, backfill, then set NOT NULL, all in one migration.
- **Seed upserts**: always pass the same full object to both `update` and `create` (`update: {}` never backfills fields added later). The deliberate exception is the `TaxFeeConfig` singleton, whose admin-set values must never be reset. The seed needs `SEED_ADMIN_PASSWORD` (12+ chars), refuses to run without it, and never prints it. **Never write a password literal into code or docs.**
- **Next.js 16**: middleware is `src/proxy.ts`, and the exported function must be named `proxy`. It does an Edge-only JWT-signature check for `/crm/**` and `/admin/**` and cannot query the DB. The authoritative checks are `getStaffSession()` / `requirePermission()` in layouts and every API route.
- **`react-hooks/set-state-in-effect`**: this lint rule traces any call chain from an effect to a `setState`. The only fix is an async function declared *locally inside* the effect body (with a `cancelled` flag), not a `useCallback` referenced from outside.
- **Strict Mode effects**: never put a ref-based "already ran" guard on a scheduled effect. It defeats Strict Mode's cleanup-and-reschedule and the timer never fires (this bit `/ai`'s initial `?q=` reply).
- **HTTP method mismatch**: `tsc`/lint/build can't catch a client helper (`postJson`/`patchJson`/`getJson` in `src/lib/api/client.ts`) calling a route that doesn't export that method, which fails silently with 405. Grep the route's exported methods.
- **No global `db` inside `db.$transaction`**: helpers that use the global client inside a transaction deadlock `prisma dev` (P2028). Pass `tx`, or look the value up before the transaction.
- **Lazily-synced state**: `syncExpiredQuotations()` must be called by every endpoint that reads quotations, not just one.
- **Multi-step forms**: every stepper nav button stays `type="button"`, including final submit (which calls `methods.handleSubmit(onSubmit)` from `onClick`). New service flows go through `MultiStepRequestFlow.tsx` + `RequestSuccessPanel.tsx` + the `src/components/forms/*` field primitives. Keep zod schema Input = Output (no `z.coerce`) so the generic `ZodType<T, T>` typing holds.
- **Keyword classifiers** (WhatsApp bot fallback): check question-shape before topic keywords, and include bare trigger words ("agent") as well as longer phrases.
- **RBAC self-lockout**: `src/lib/auth/admin-guard.ts` blocks removing the last active `admin.full` holder. Only an `admin.full` user can grant `admin.full`, and nobody can change their own role (P03).
- **Mock services mirror real crypto**: every mock gateway uses the same HMAC scheme as the real one with a different secret, so verification code is really exercised.

## Progress so far — Data model & core pipeline
- **Schema** (`prisma/schema.prisma`, migrations in `prisma/migrations/`, latest `20260930220000_go_live_flag`). The core chain is Customer → Passenger/Lead → Quotation → Booking (+ `BookingPassenger`) → Payment (+ `PaymentWebhookEvent`) → Refund. Around it: Document + `DocumentExtraction` (OCR), AuditTrail (polymorphic), Task, per-service `ServiceStatus`/`ServiceStatusTransition`, Vendor/`VendorService`/`VendorScoringConfig`, and RBAC (User/Role/Permission). Masters and config: Service, Country, VisaType, Nationality, Occupation, Airport, Airline, Border, DocumentRequirement, PricingRule, Coupon/`CouponConfig`, Faq, NotificationTemplate, TaxFeeConfig, InvoiceConfig, SystemConfig (singleton), RefundConfig, ServiceTerms, ServiceTimelineConfig, OtbRuleConfig, OtbPrice, ReturnTicketDestination, NewVisaCountryConfig, ProtectionPlan*, Holiday, KnowledgeArticle, ExpenseCategory/Expense, StaffLeave. Infrastructure: `RateLimitBucket`, `FileBlob`, `ReferenceCounter`, `InvoiceCounter`, WhatsApp conversation/log, AutomationRun/AutomationReminderLog. For models added in P21–P24, see below. Status fields are enums, and the coarse `LeadStatus`/`BookingStatus` are kept in sync by the per-service status engine.
- **Lead intake**: `src/lib/leads/create-lead.ts`'s `createLeadFromSubmission()` is the single pipeline for website, WhatsApp bot, contact form and manual leads. It matches or creates the Customer (mobile, then email) and the Passengers, creates the Lead, writes the audit row, notifies the customer and staff, and runs auto-assignment. Reuse it; don't hand-roll matching.
- **References (P07, locked)**: Lead reference = `1 + MM + YY + ServiceCode + monthly sequence` (e.g. `10626VI001`). It is race-safe via `ReferenceCounter`, and `Service.referenceCode` is editable in Admin. **The Booking ID is the lead's own reference** (`src/lib/bookings/reference.ts` `bookingIdForLead`, with `-2`, `-3`… for a later booking on the same lead). There are no placeholders and no `TNX-` ids for new bookings; old `NV-`/`OTB-`/`TNX-` references still resolve. Invoices are numbered `INV-2026-27-0001` via `InvoiceCounter`.
- **Per-service status engine (P08)**: `src/lib/service-status/engine.ts` `setServiceStatus()` / `setServiceStatusByEvent()` validates each move against `ServiceStatusTransition`, audits old→new, syncs the coarse status via `mapsTo*`, and fires the status's `notificationEvent`. System events only move forward, never out of a terminal status or On Hold. The CRM "Change Status" control shows only the allowed next statuses. Customers see `ServiceStatus.customerLabel` (`src/lib/service-status/customer-label.ts`). `ServiceStatus.blocksRefund` drives the refund engine.
- **Quotations**: one `Quotation` model with a flight shape (`FLIGHT_SPECIAL_FARE`) and a fee shape (`src/lib/quotations/pricing.ts`, decided by the lead's server-side `serviceType`). `margin = sellingPrice − vendorCost` is always computed server-side. Selecting a quote expires its siblings. `syncExpiredQuotations()` never expires a selected or paid quote. Flight quotes have a 30-minute validity cap, a live countdown, and an alternative route via `alternativeOfId`. `assertQuotationPayable()` blocks payment on an expired quote across every payment path (P01). Drafts, revisions and a multi-sector itinerary were added in P22.
- **Payments**: `src/lib/payments/` has a `PaymentGateway` interface, `razorpay-gateway.ts` (Payment Links API) and `mock-gateway.ts`. **In production, missing Razorpay keys are a hard error, never a mock fallback** (P01), and `/api/pay/[token]/mock-pay` returns 404 in production. The webhook `/api/webhooks/razorpay` reads the raw body, verifies the HMAC, is idempotent per gateway event (`PaymentWebhookEvent`), and checks amount + currency against the Payment total (a mismatch is audited `PAYMENT_AMOUNT_MISMATCH` and does not complete). `completePaymentSuccess()` (`complete-payment.ts`) is shared by the webhook and manual mark-success. Mark-success is blocked for bank transfers, which go through the `payments.approve` approval with a slip, and the approver can't be the creator. The customer pay page is `/pay/[token]` and requires Terms acceptance (P09). Totals subtract `couponDiscount`. GST and gateway-fee rates come from `TaxFeeConfig` via `getTaxFeeRates()`. **GST is locked at 0%** until the client registers a GSTIN; Admin shows a warning and go-live is blocked if it's above 0. Invoices are rendered by `src/lib/invoices/render-invoice.ts` (pdfkit), with a non-GST invoice while GST is off.
- **Refunds**: `src/lib/refunds/rules.ts` reads the per-service `RefundConfig` (Admin → Service Configuration → Refund config) and `ServiceStatus.blocksRefund`. `paidAmount` is computed from the Payment, never from the request. The sum of non-rejected refunds can't exceed the paid amount. The raiser can't approve their own refund (`Refund.raisedByUserId`, `refunds.approve`). A fully refunded booking moves to `REFUNDED`.
- **Documents & files (P02)**: uploads are validated server-side (size + magic-byte MIME, max 8MB decoded, 413 when oversize) and stored privately (`src/lib/storage/local-file-storage.ts`: `storage/uploads/` on disk, or `FileBlob` in the DB on serverless / `FILE_STORAGE=db`). They are served **only** via `/api/files/[id]`, which requires staff `documents.view` + service scope, the owning customer's session, or a valid pay/quote token. Nothing is written under `public/uploads` anymore (legacy files there are still readable). Document status transitions are enforced (REQUIRED/MISSING → RECEIVED → VERIFIED/REJECTED, REJECTED → RECEIVED), and rejection needs a reason. Output delivery (P09, `src/lib/outputs/deliver-output.ts`) covers VISA_PDF, EXTENDED_VISA_PDF, TICKET_PDF, RESERVATION_PDF, PACKAGE_PDF and OTB_CONFIRMATION: it saves the document, moves the service status, and notifies the customer via the `OUTPUT_DELIVERED` event.
- **Audit**: every mutation writes through `src/lib/audit/log.ts`'s `writeAudit(tx, …)` with `byUserId` and a "(by Name)" note. Timelines come from `src/lib/audit/timeline.ts` / `booking-timeline.ts`.
- **API conventions**: `src/lib/api/respond.ts` (`jsonSuccess`/`jsonError` → `{ data }` / `{ error: { message, fieldErrors? } }`) and `src/lib/api/client.ts` (`getJson`/`postJson`/`patchJson`, which throw `ApiError`). State-changing cookie-authenticated routes check `Origin`. Rate limiting is DB-backed (`src/lib/auth/rate-limit.ts`, `RateLimitBucket`) so it works on serverless. Security headers (CSP, HSTS, frame-deny, etc.) are set in `next.config.ts`.

## Deployment
Production (tripnexio.com) is a Hostinger VPS running Coolify; pushing to GitHub does not deploy by itself. Order: push `master` → on the VPS back up the Postgres container (`pg_dump` → `/root/backups/pre-deploy-<timestamp>.sql.gz`) → trigger the Coolify deploy through its API (token in `/root/.coolify-token`, app/db ids in `/root/tripnexio-coolify.ids`) → poll the deployment until `finished`. Migrations run with `prisma migrate deploy` when the container starts; confirm the new migration in the deploy log. Coolify does a rolling update, so a failed build leaves the previous version serving. Runtime env vars are edited through the Coolify API (never print values). The go-live checklist is in README.md.
